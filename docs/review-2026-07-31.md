## 严重问题 (应优先修复)

### C1. canal-client 丢失 row_change 和 ddl_sql 数据

**文件**: `crates/canal-client/src/lib.rs:255-293`

`entry_bytes_to_event()` 只解析了 protobuf Entry 的 Header，完全忽略 `store_value` 中的 `RowChange`。客户端收到的 event 的 `row_change` 和 `ddl_sql` 永远是 `None`，客户端订阅者拿不到任何行级变更数据。

**修复**: 从 `entry.store_value` 解码 `RowChange`，还原 before/after columns 和 DDL SQL。

### C2. MemoryEventStore::get_batch() 无超时，永久阻塞

**文件**: `crates/canal-store/src/memory.rs:78-113`

当客户端请求的位置超出 store 最新数据时，`get_batch()` 循环等待 `notify.notified().await` 永不返回。binlog 停止产生事件后所有客户端永久挂起。

**修复**: 使用 `tokio::time::timeout` 包装等待，超时返回空 Events。

### C3. CanalServer 缺少优雅关闭

**文件**: `crates/canal-server/src/server.rs:65`

`serve()` 的 `loop { ... }` 永不退出，外部代码无法停止服务器。

**修复**: 接受 `CancellationToken` 或 `watch::Receiver<bool>` 作为关闭信号。

### C4. DefaultBinlogConnector::running 存在数据竞争

**文件**: `crates/canal-binlog/src/connector.rs:49`

`running: bool` 在 async context 中被读写但无同步保护。`connect()` 设置它后 spawn blocking task，`disconnect()` 再设置。并发重连调用会导致 UB。

**修复**: 改为 `AtomicBool`。

### C5. KafkaConnector 在构造函数中就创建 producer

**文件**: `crates/canal-connector/src/kafka.rs:29`

`KafkaConnector::new()` 立即调用 `ClientConfig::new().create()`。如果 Kafka 不可达，连 Instance 都无法构造。与 `SinkConnector` trait 的设计冲突（trait 显式分离了 new 和 connect）。

**修复**: 将 producer 创建延迟到 `connect()` 中。

## 中等问题

### M1. LogPosition 字典序比较对 binlog 轮转不正确

**文件**: `crates/canal-store/src/memory.rs:87-88`

`(journal_name, position) > (start.journal_name, start.position)` 使用字符串字典序。当 binlog 从 `mysql-bin.000009` 轮转到 `mysql-bin.000010` 时，字典序 `"000010" < "000009"`（因为 `'1' < '9'`），导致位置比较方向错误。

**修复**: 为 `LogPosition` 实现 `Ord`，解析文件名数值后缀后比较。

### M2. Admin API 与 Instance 管理脱节

**文件**: `crates/canal-admin/src/lib.rs:112-136`

`start_instance()` / `stop_instance()` 只修改 `AdminInstance.running` 布尔值，完全不与 `CanalInstance`/`InstanceManager` 交互。管理员通过 REST API 操作实例不会有实际效果。

**修复**: 让 `AdminState` 持有 `Arc<InstanceManager>`，handler 调用实际启停方法。

### M3. Kafka dispatch 用 events[0] 的 schema 做所有消息 key

**文件**: `crates/canal-connector/src/kafka.rs:129`

```rust
.key(&events[0].schema_name)
```

一个 batch 跨不同 schema 时所有消息用首条事件的分区键，违背按 schema 分区的意图。

**修复**: 每条消息使用自己对应 event 的 schema_name。

### M4. DefaultBinlogConnector::take_receiver() 在 connect 后调用会出错

**文件**: `crates/canal-binlog/src/connector.rs:367-380`

如果 `connect()` 已调用，spawn_blocking 持有旧 sender 在发送事件。调用 `take_receiver()` 会取出旧 sender 创建新 channel，新 channel 永远收不到消息。

**修复**: 添加运行时检查或文档说明必须在 `connect()` 之前调用。

### M5. DefaultEventSink 对 connector 失败静默处理

**文件**: `crates/canal-sink/src/sink.rs:106-110`

Connector dispatch 失败只记录 `error!()`，`sink()` 仍返回 `Ok(Events)`。调用者无法得知事件部分投递失败。

**修复**: 收集失败计数并记录到 metrics 或返回带 warning 的 Result。

## 代码质量

### Q1. CLI 配置加载代码重复

`run_server` 和 `run_dump` 有相同的配置加载逻辑（~5 行）。应提取为 `fn load_config(path: &Path) -> Result<CanalConfig>`。

### Q2. handle_client 函数过长

**文件**: `crates/canal-server/src/server.rs:92-306` (~215 行)

处理 6 种 packet type，应拆分为独立 handler 函数 `handle_auth`, `handle_sub`, `handle_get` 等。

### Q3. get_batch 的 position_range.start 语义不直观

`sink.rs:93` 使用 `position.saturating_sub(1)` 作为 start position。因为 get_batch 使用 `>` 严格大于比较，所以必须减 1 才能匹配到该 position 的事件。建议让比较语义更清晰。

### Q4. canal-proto 不必要依赖 canal-common

**文件**: `crates/canal-proto/Cargo.toml`

声明了 `canal-common` 依赖但 `lib.rs` 中未使用，造成不必要的重编译链。

### Q5. 缺少 public API 文档

`CanalInstance`, `InstanceManager`, `CanalServer`, `CanalClient` 等关键公开类型缺少 doc comments 和使用示例。

### Q6. 缺少集成测试

所有 100 个测试都是单元测试，没有端到端测试验证完整链路。

## 性能优化

### P1. MemoryEventStore::get_batch() O(n) 线性扫描

**文件**: `crates/canal-store/src/memory.rs:86-89`

`buffer.iter().position()` 每次请求都扫描整个 buffer。在大缓冲 (16384)、多客户端场景下开销显著。

**建议**: 维护 `(journal_name, position) -> buffer_index` 的有序索引。

### P2. DefaultEventSink::sink() 中事件被多次克隆

filtered events 被 clone 三次：`put_batch(filtered.clone())` → `Arc::new(filtered)` → `(*events).clone()`。

**建议**: 先用 `Arc<Vec<CanalEvent>>` 包装，之后只 clone Arc（引用计数）。

### P3. CanalCodec::decode() 每次分配 Vec

每个 packet 通过 `src[..len].to_vec()` 分配新内存。可考虑返回 `Bytes` 或使用 `split_to()`。

## 安全审查

### S1. 密码明文存储

MySQL 密码在 `DefaultBinlogConnector` 和 CLI config 中以 `String` 存储。建议使用 `secrecy::Secret<String>` 保护内存中的敏感数据。

### S2. 协议无认证验证

**文件**: `crates/canal-server/src/server.rs:117`

`ClientAuth` 的 `username`/`password` 被解析但从未校验。任何 TCP 连接都可获取所有 binlog 事件。

### S3. 网络传输无加密

TCP 协议无 TLS。生产跨网络部署时 binlog 数据明文传输。

## 架构评估

15 个 crate 分层清晰：

- **协议层**: canal-proto (protobuf), canal-common (共享类型/错误)
- **数据面**: canal-binlog (MySQL CDC), canal-store (事件存储), canal-filter (过滤)
- **流出**: canal-sink (分发), canal-connector (Kafka 等外部系统)
- **控制面**: canal-server (TCP 服务端), canal-client (客户端 SDK), canal-instance (实例管理)
- **运维**: canal-admin (REST API), canal-prometheus (指标), canal-meta (元数据), canal-cli (CLI)

与 Java Canal 功能对齐度：

| 模块 | 完成度 | 说明 |
|------|--------|------|
| 协议兼容 | 100% | protobuf 完整，codec 兼容 |
| TCP 服务端 | 90% | AUTH/SUB/GET/ACK/Rollback/Heartbeat，缺优雅关闭 |
| 客户端 | 60% | TCP 握手完整，**但丢失 row_change/ddl_sql 数据** |
| Binlog 解析 | 85% | INSERT/UPDATE/DELETE/DDL/Query，GTID 未完整实现 |
| 事件存储 | 80% | Ring buffer，缺磁盘持久化和超时机制 |
| 过滤 | 90% | 正则匹配，缺 Aviator 表达式 |
| Kafka 投递 | 80% | 同步投递，缺异步批量和 Exactly-Once |
| 实例管理 | 85% | 多实例生命周期，缺 HA |
| Admin REST | 60% | 基础端点，**不与 InstanceManager 联动** |
| Prometheus | 80% | 基础 Counter/Gauge，缺 Histogram |
