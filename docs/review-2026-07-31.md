## 警告级别问题 (Warning)

### W1. `workspace.package.name` 是无效的 manifest key

**文件**: `/Cargo.toml:6`

`name = "canal-rust"` 放在 `[workspace.package]` 下无效。`name` 只对 `[package]` 有效。每次构建产生 warning: `unused manifest key: workspace.package.name`

**修复**: 从 `[workspace.package]` 删除 `name` 行。

---

### W2. 9 处 `field_reassign_with_default` Clippy 警告

**文件**: `crates/canal-server/src/server.rs` (行 745-746, 764-766, 801-802, 805-806, 836-837, 858-859, 880-881, 901-902, 921-922)

测试代码中使用 `let mut packet = Packet::default(); packet.r#type = ...;` 模式，应改为结构体字面量:

```rust
let packet = Packet {
    r#type: PacketType::Ack as i32,
    body: ack.encode_to_vec(),
    ..Default::default()
};
```

**文件**: `crates/canal-server/Cargo.toml:13,22`

`futures = "0.3"` 同时出现在 `[dependencies]` 和 `[dev-dependencies]`，应改为 `futures.workspace = true` 与 workspace 根保持一致。

### W5. `MemoryEventStore::first_position` 在 ring buffer 淘汰事件后变为过时值

**文件**: `crates/canal-store/src/memory.rs:54-57`

`first_position` 仅在 buffer 为空时设置。当 buffer 满时 `pop_front()` 淘汰旧事件后（第 50 行），`first_position` 未更新。

**场景**: buffer 容量 2。存入位置 100 和 200 → `first_position` = 100。再存入 300，淘汰 100 → buffer 为 [200, 300]，但 `first_position()` 仍返回 100（该位置事件已被淘汰）。

**修复**: `pop_front()` 后从新的队首元素更新 `first_position`。

---

### W6. Binlog 日志轮转会导致 `get_batch` 永久阻塞

**文件**: `crates/canal-store/src/memory.rs:81-83`

位置比较要求 `journal_name` 精确匹配。MySQL 日志轮转后（`mysql-bin.000001` → `mysql-bin.000002`），客户端请求旧 journal 中位置时永远找不到新 journal 中的事件。

**场景**: 客户端 ACK `mysql-bin.000001:99999`。MySQL 轮转到 `mysql-bin.000002`。新事件 journal_name 为 `mysql-bin.000002`。客户端请求 `mysql-bin.000001:99999` 之后的事件 — buffer 中无匹配，`get_batch` 永久循环等待。

**修复**: 使用字典序比较 `(journal_name, position)` 元组，正确处理轮转。

---

### W7. Kafka 分发静默接受部分投递失败为成功

**文件**: `crates/canal-connector/src/kafka.rs:136-143`

消息投递失败仅记录日志，循环继续，函数最终返回 `Ok(())`。如果 10 条消息中 5 条失败，调用方看到成功但数据已丢失。

**修复**: 跟踪失败数，`delivered < total` 时返回错误。

---

### W8. `EventSink::sink()` 对每个 connector 重复 clone 事件

**文件**: `crates/canal-sink/src/sink.rs:91-95`

`filtered.clone()` 在 connector 循环中每次迭代都调用。N 个 connector + M 个事件 = N+1 次完整 clone。

**修复**: 使用 `Arc<Vec<CanalEvent>>` 共享数据。

## 信息级别问题 (Info)

### I1. `KafkaConnector::new()` 构造失败时 panic

**文件**: `crates/canal-connector/src/kafka.rs:34`

`.expect("Failed to create Kafka producer")` 在库 crate 中 panic 不可接受。应返回 `Result`。

### I2. `CanalClient` 是桩代码

**文件**: `crates/canal-client/src/lib.rs`

- `#[allow(dead_code)]` — 结构体未被使用
- `connect()` 仅设置 `connected = true`，无实际 TCP 连接
- `subscribe()` 创建 channel 但不启动填充任务
- `CanalEventStream` 无法接收任何事件

**建议**: 实现完成前移除或标记为未完成。

### I3. CLI `server` 命令未接入 binlog connector

**文件**: `crates/canal-cli/src/main.rs:145-148`

创建了 `MemoryEventStore` 和 `CanalServer` 但未创建 `DefaultBinlogConnector`。服务器可接受连接但 `get_batch` 永久阻塞 — 无数据源。

### I4. CLI `dump` 命令未实现

**文件**: `crates/canal-cli/src/main.rs:153-164`

仅打印占位消息，无实际 MySQL 连接或 binlog 处理。

### I5. `get_batch` 每次批量 clone 事件

**文件**: `crates/canal-store/src/memory.rs:88`

`.cloned().collect()` 对批次中每个 `CanalEvent` 进行 clone。大批次时内存开销显著。未来可考虑 `Arc<CanalEvent>`。

### I6. 缺少端到端集成测试

77 个单元测试覆盖隔离功能，但无验证完整管道的集成测试: `connector → filter → sink → store → server → client`。

### I7. `canal-common` 和 `canal-proto` 无直接单元测试

作为基础库（7 个源文件），正确性仅通过下游 crate 间接验证。
