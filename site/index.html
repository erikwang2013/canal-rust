01 / WHY

同一条 wire protocol，
更轻的运行时。

不改客户端，不改协议，只把 JVM 换成原生二进制。Canal Rust 保留了 Java Canal 的协议语义，同时把整条链路拆成 14 个可以独立演进的 crate。

Workspace

14

个 crate，各守一段运河

接入、处理、输出、编排、运维、基础六层解耦。每一层都可以单独编译、测试和替换。

binlogfilterstoresinkserverconnector

Ingest

实时 binlog 解析

基于 mysql_cdc 连接 MySQL 5.1–8.0 / MariaDB，支持 position 与 GTID 位点，把 TableMap 映射成统一事件模型。

Backpressure

环形缓冲与消费 Ack

内存 ring buffer 保存事件，容量溢出自动淘汰；客户端确认消费后推进位点，不让下游被淹没。

Operate

一个进程，多个出口

单进程运行多个 destination；事件可扇出到 TCP 客户端或 Kafka，Prometheus 指标和 Admin API 一并带上。

02 / FLOW

一条事件，六段旅程。

从 MySQL 的 binlog 到下游消费者，每一次变更都被接住、检查、排队、送出， 直到客户端确认。哪一段慢了，都能在指标里看见。

接入
canal-binlog 连接 MySQL、拉取 binlog，转换为统一事件模型。
处理
canal-filter 正则过滤库表，canal-sink 把事件扇出到多个出口。
输出
canal-store 环形缓冲，canal-server 提供 TCP 协议，canal-connector 投递 Kafka。
编排
canal-instance 管理多个 destination，每个实例独占一条完整链路。
运维
canal-admin 启停 API、canal-prometheus 指标、canal-cli 命令行入口。
基础
canal-common 类型与生命周期、canal-proto protobuf 生成、canal-meta 表结构缓存。

03 / MASCOT

守闸的小运，
也有十二张脸。

项目宠物不是一个贴纸，而是这条链路的角色化解释：流量要有人控制， 事件要有人送达。小运站在闸墙上，顺便把 Rust、ring buffer 和 fan-out 都演了一遍。

小运是这条数据运河的闸官。锈红色外壳对应 Rust；左钳拧着闸门水轮， 决定放多少数据过去；右钳托着一枚发光的事件，把变更送往下游。上游还漂着一卷 binlog 日志，闸下的水里是已经放行的数据包。

锈红色外壳Rust
闸门水轮canal-store · ring buffer
右钳托着的事件canal-sink · fan-out
闸下漂着的包canal-server / canal-connector
上游的 binlog 卷轴canal-binlog

GET STARTED

五分钟，把运河接通。

装好 protoc，clone、build、改一份 canal.yaml，然后让小运开始守闸。

安装文档 → 使用说明
terminal
# 需要 Rust 1.85+ 与 protoc
git clone https://github.com/erikwang2013/canal-rust.git
cd canal-rust
cargo build --release
./target/release/canal-rust server --config canal.yaml
